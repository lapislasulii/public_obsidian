# Воркшоп по структурным паттернам

> [!WARNING] Качество источника
> Больше половины абзацев транскрибации распознаны ненадёжно (код диктовался голосом, распознаватель путал идентификаторы). Код ниже восстановлен по смыслу рассказа: идея и структура взяты из записи, точные имена и синтаксис надо сверить с репозиторием воркшопа.

## Обзор лекции

Практическое занятие: с нуля собирается .NET-решение в Rider, и на нём разбираются структурные паттерны (теория в [[Структурные паттерны проектирования]]). Домен — дерево математических выражений: константы, переменные, четыре арифметические операции, унарный минус, полное и частичное вычисление. По ходу показаны контекст как объект параметров, Try-паттерн, результат-тип с двумя исходами, switch по кортежу с pattern matching, Composite, Bridge, Adapter, Decorator, Proxy с кэшированием, методы и блоки расширения, `using static` и мини-DSL для построения выражений.

## Предварительные сведения

- Интерфейсы, полиморфизм, принципы проектирования — см. [[SOLID и GRASP]] и [[Введение]].
- Базовый синтаксис C#: классы, `record`, `Dictionary<TKey, TValue>`.
- Git: репозиторий, `.gitignore`.

## 1. Создание решения: dotnet CLI и Rider

При установке .NET SDK появляется консольная утилита `dotnet`. Все действия IDE (build, run, test) — по сути её вызовы.

- `dotnet new` создаёт проекты и файлы по шаблонам.
- `dotnet new sln` создаёт **solution** — входную точку, глобальный манифест структуры: перечисляет все `.csproj` (отдельные проекты). В шаблонном репозитории курса это файл формата `.slnx` (новый XML-формат решения).
- `Directory.Build.props` — XML с общими настройками, которые автоматически подключаются во все `.csproj` ниже по дереву каталогов (версия target framework, версия языка, анализаторы). Нужен, чтобы настройки не расходились между проектами.
- `Directory.Packages.props` — централизованное управление версиями NuGet-пакетов: во всех проектах используется одна и та же версия библиотеки, что спасает от конфликтов версий зависимостей. Пакеты обычно ставят через UI IDE или `dotnet add package`, руками файл правят редко.

**Первый шаг после создания git-репозитория — `.gitignore`.** До него даже не стоит открывать IDE: IDE создают служебные папки с конфигами, которые не должны попадать в VCS. Сгенерировать его можно командой `dotnet new gitignore`.

Общие настройки из `.csproj` переносятся в `Directory.Build.props`, например:

```xml
<Project>
  <PropertyGroup>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
```

- `ImplicitUsings` — компилятор сам подключает часто используемые пространства имён (например, `System`, где лежат базовые типы: `int` это `System.Int32`).
- `Nullable` — включает nullable reference types: синтаксис с `?` показывает, где допустим `null`, а где нет, и компилятор предупреждает о возможных `NullReferenceException`.

Для экспериментов создаётся отдельный консольный проект, в который добавляется ссылка на проект с выражениями (`<ProjectReference>`; так же тесты подключены к проектам в шаблоне курса).

## 2. Домен и постановка задачи

Требования: выражения из констант, переменных и операций $+, -, \times, /$; отрицание выражения; форматирование в строку; вычисление, в том числе **частичное**: известные переменные подставляются и всё, что можно, сворачивается в число, остальное остаётся выражением. Система должна быть расширяемой.

Сначала лектор показал плохой вариант: один класс с полем-перечислением типа узла (`Constant`, `Variable`, `Sum`, ...) и набором полей «на все случаи» (число, имя, левый и правый операнды). Работать с ним тяжело: каждая операция превращается в большой `switch`, половина полей пустует.

Дерево выражений естественно ложится на полиморфизм: каждый вид узла хранит свои данные и имеет своё поведение.

```csharp
public interface IExpression
{
    string Format();
    ExpressionEvaluationResult Evaluate(ExpressionEvaluationContext context);
}
```

`Format` нужен, потому что объект в отладчике выглядит непонятно; хочется видеть выражение строкой.

## 3. Контекст вычисления (объект параметров)

Значения переменных — параметры вычисления, а не состояние выражения: одно и то же выражение хочется вычислять при разных наборах $x_1, x_2, \ldots$

Передавать в `Evaluate` словарь напрямую плохо: если позже понадобится ещё какой-то параметр вычисления, придётся менять сигнатуру во всех классах-выражениях. Поэтому данные выносятся в отдельный тип — **контекст** (иногда его называют request). Изменение состава данных затрагивает только этот класс.

```csharp
public sealed class ExpressionEvaluationContext
{
    private readonly Dictionary<string, double> _variables = new();

    public void AddVariable(string name, double value) => _variables[name] = value;

    public bool TryGetVariableValue(string name, out double value)
        => _variables.TryGetValue(name, out value);
}
```

### Try-паттерн

Метод возвращает `bool` (успех или нет), а сам результат кладёт в `out`-параметр. Вызываемый метод обязан записать значение в `out`-переменную.

```csharp
var dict = new Dictionary<string, double>();
Console.WriteLine(dict.TryGetValue("x", out double v) ? v : null); // пусто
dict["x"] = 2;
Console.WriteLine(dict.TryGetValue("x", out v) ? v : null);        // 2

Console.WriteLine(int.TryParse("1", out int r));    // True, r = 1
Console.WriteLine(int.TryParse("1abc", out r));     // False
```

Подходит для простых операций, где важен только факт успеха: заводить для этого полноценный result-тип было бы избыточно. Лектор уточнил, что это скорее подход (идиома), чем паттерн проектирования.

## 4. Результат вычисления

У вычисления два исхода — полностью вычислено (число) или частично (упрощённое выражение). Это моделируется абстрактным record с двумя наследниками:

```csharp
public abstract record ExpressionEvaluationResult
{
    private ExpressionEvaluationResult() { }

    public sealed record Success(double Value) : ExpressionEvaluationResult;
    public sealed record Partial(IExpression Expression) : ExpressionEvaluationResult;
}
```

> [!NOTE] Дополнено
> Приватный конструктор закрывает иерархию: наследники могут быть только вложенными. В записи прозвучало лишь «абстрактный record и два кейса».

Ошибки вроде деления на ноль отдельным исходом не делают: `double` умеет хранить бесконечность и `NaN`. Действительно исключительные ситуации (например, переполнение, если его проверять) — повод для исключения, а не для ещё одного варианта результата.

Record автоматически генерирует `ToString` с именем типа и свойствами; чтобы в консоли печаталось просто значение, `ToString` можно переопределить.

## 5. Листья: константа и переменная

```csharp
public sealed record ConstantExpression(double Value) : IExpression
{
    public string Format() => Value.ToString(CultureInfo.InvariantCulture);

    public ExpressionEvaluationResult Evaluate(ExpressionEvaluationContext context)
        => new ExpressionEvaluationResult.Success(Value);
}

public sealed record VariableExpression(string Name) : IExpression
{
    public string Format() => Name;

    public ExpressionEvaluationResult Evaluate(ExpressionEvaluationContext context)
        => context.TryGetVariableValue(Name, out double value)
            ? new ExpressionEvaluationResult.Success(value)
            : new ExpressionEvaluationResult.Partial(this);
}
```

- `CultureInfo.InvariantCulture`: по умолчанию формат числа берётся из локали машины (разделитель дробной части может быть запятой, как в Excel или Google Таблицах). Invariant culture везде даёт точку — вывод одинаков на всех компьютерах.
- Константу можно считать **адаптером** между `double` и интерфейсом `IExpression` (если сознательно притягивать паттерны).
- Если переменной нет в контексте, она «вычислена частично», то есть никак: это атомарная единица, и возвращается она сама. Возвращать `this` безопасно, потому что объекты неизменяемые.

## 6. Сумма: Composite и switch по кортежу

Сумма — объект, реализующий `IExpression` и содержащий внутри другие `IExpression`. Это **Composite (компоновщик)**: из таких узлов собирается дерево выражений.

Каждый операнд может вычислиться полностью или частично, итого $2 \times 2 = 4$ исхода. Удобный инструмент — `switch`-выражение по кортежу с pattern matching (сопоставление не только по равенству, как в C/C++, но и по типу с одновременным объявлением переменной, как в `is`):

```csharp
public ExpressionEvaluationResult Evaluate(ExpressionEvaluationContext context)
{
    return (Left.Evaluate(context), Right.Evaluate(context)) switch
    {
        (Success l, Success r) => new Success(l.Value + r.Value),
        (Success l, Partial r) => new Partial(new SumExpression(new ConstantExpression(l.Value), r.Expression)),
        (Partial l, Success r) => new Partial(new SumExpression(l.Expression, new ConstantExpression(r.Value))),
        (Partial l, Partial r) => new Partial(new SumExpression(l.Expression, r.Expression)),
    };
}
```

Компилятор C# всё равно предупреждает о неполноте `switch`: в языке нет union-типов, и он не может доказать, что четыре варианта исчерпывают всё. В функциональных языках компилятор умеет это проверять.

Пример: для $x + 1$ без значения $x$ получаем частичный результат `x + 1`; при заданном $x$ — число.

## 7. Bridge: выделение бинарного оператора

Писать этот класс ещё трижды (для $-, \times, /$) не хочется: от конкретной операции в нём зависят только два места — символ при форматировании и само арифметическое действие. Выделяем низкоуровневую абстракцию:

```csharp
public interface IBinaryOperator
{
    string Format(string left, string right);
    double Evaluate(double left, double right);
}

public sealed class AdditionOperator : IBinaryOperator
{
    public string Format(string left, string right) => $"({left} + {right})";
    public double Evaluate(double left, double right) => left + right;
}
```

Операторы — очень маленькие классы с минимумом ответственности; остальные три пишутся аналогично. Узел дерева становится универсальным `BinaryOperatorExpression(IExpression Left, IExpression Right, IBinaryOperator Operator)`: в `Format` он вызывает `Operator.Format(Left.Format(), Right.Format())`, в `Evaluate` вместо `+` — `Operator.Evaluate(l, r)`, а в частичных ветках передаёт тот же оператор в новый узел.

Почему это **мост**: высокоуровневая абстракция — `IExpression` со всей логикой полного и частичного вычисления, низкоуровневая — `IBinaryOperator`, у которой большой потенциал переиспользования (она ничего не знает о выражениях). Класс `BinaryOperatorExpression` их соединяет, и обе стороны могут меняться независимо. Можно придумать другую реализацию выражения поверх тех же операторов, или оператор, комбинирующий два других.

Этот класс одновременно мост, адаптер и компоновщик: паттерны в реальном коде часто смешиваются.

## 8. Методы расширения и блоки extension

**Метод расширения** — статический метод, который можно вызывать через точку, как метод объекта. Так устроен LINQ (`Where`, `Select`): методы написаны один раз для `IEnumerable<T>` и работают для любой коллекции, включая ваши собственные.

```csharp
public static class EnumerableExtensions
{
    public static double MySum(this IEnumerable<double> values)
    {
        double result = 0;
        foreach (var v in values) result += v;
        return result;
    }
}

// EnumerableExtensions.MySum(a)  эквивалентно  a.MySum()
```

Без расширений цепочки вызовов были бы вложенными и читались бы изнутри наружу, как `map(filter(...))` в Python. Ключевое слово `this` перед первым параметром — всё, что нужно. Метод при этом остаётся внешним статическим: к приватным полям и методам типа он доступа не имеет. В Rider можно посмотреть понижённый (lowered) код — после преобразования компилятором вызов через точку превращается в обычный вызов статического метода.

Новая возможность языка — **блоки extension**: работают по тому же принципу, но позволяют добавлять не только методы, а ещё свойства, статические члены и операторы.

> [!WARNING] Восстановлено
> Синтаксис ниже восстановлен по описанию; это нововведение C# 14 *(дополнено: версия языка в записи не названа)*.

```csharp
public static class ExpressionExtensions
{
    extension(IExpression)
    {
        public static IExpression operator +(IExpression left, IExpression right)
            => new BinaryOperatorExpression(left, right, new AdditionOperator());
    }
}
```

После этого можно писать `new VariableExpression("x") + new ConstantExpression(1)` — то же самое дерево, только через оператор.

## 9. Мини-DSL: фабричные методы и using static

Явные `new VariableExpression(...)` выглядят ненатурально. Добавляем статические фабрики:

```csharp
public static IExpression Constant(double value) => new ConstantExpression(value);
public static IExpression Variable(string name) => new VariableExpression(name);
```

`using static` подключает в файл не типы из пространства имён, а статические члены класса (instance-члены подключить нельзя, это очевидно). Их можно вызывать так, будто они объявлены в этом же файле:

```csharp
using static Expressions.ExpressionExtensions;

var e = -Variable("x") + Constant(2);
```

Такой подход — подстроить объектную модель и синтаксис так, чтобы код выражал домен, — называется **DSL** (domain-specific language), здесь внутренний: язык тот же, просто красиво оформленный. Ядро остаётся модульным, и с объектной моделью можно работать и без «сахара». Особенно приятно так писать тесты.

## 10. Унарный минус: Decorator

Чтобы добавить отрицание к любому выражению, используется **декоратор**: `NegateExpression` хранит вложенное `IExpression` и сам реализует тот же интерфейс.

```csharp
public sealed record NegateExpression(IExpression Expression) : IExpression
{
    public string Format() => $"-{Expression.Format()}";

    public ExpressionEvaluationResult Evaluate(ExpressionEvaluationContext context)
        => Expression.Evaluate(context) switch
        {
            Success s => new Success(-s.Value),
            Partial p => new Partial(new NegateExpression(p.Expression)),
        };
}
```

Важно: при частичном результате упрощённое выражение нужно снова обернуть в декоратор. Внутренний объект ничего не знает об отрицании, а код выше по дереву не знает о нашем декораторе — если не обернуть, минус потеряется. Всё, что проходит через декоратор, оборачивается в подобный ему объект.

В блок extension добавляется унарный `operator -`, и пример `-x + 2` работает.

## 11. Proxy: кэширование результатов оператора

Сначала создаётся проблема: «медленный» оператор-прокси, который оборачивает другой `IBinaryOperator`, форматирует так же, но вычисляет долго.

> [!WARNING] Восстановлено
> Этот фрагмент записи почти не разборчив. Из контекста: прокси имитирует дорогую операцию (вероятно, задержкой), чтобы показать, зачем нужен кэш.

Решение — **кэширующий прокси**. Применимо, потому что результат операции зависит только от входных данных (функция чистая): результат $a + b$ определяется только $a$ и $b$. Это мемоизация.

```csharp
public sealed class CachedBinaryOperator : IBinaryOperator
{
    private readonly IBinaryOperator _operator;
    private readonly Dictionary<CacheKey, double> _cache = new();

    public CachedBinaryOperator(IBinaryOperator op) => _operator = op;

    public string Format(string left, string right) => _operator.Format(left, right);

    public double Evaluate(double left, double right)
    {
        var key = new CacheKey(left, right);
        if (_cache.TryGetValue(key, out double cached)) return cached;
        double result = _operator.Evaluate(left, right);
        _cache[key] = result;
        return result;
    }

    private sealed record CacheKey(double Left, double Right);
}
```

Ключ — маленький `record`: компилятор генерирует для него конструктор, свойства и, главное, **структурное сравнение** (`Equals`/`GetHashCode` по всем свойствам). Два ключа с одинаковыми `Left` и `Right` равны, что и нужно словарю.

Оговорка лектора: `double` сравнивается точно, накопленная погрешность здесь игнорируется. В реальной системе такой кэш либо не делают для вещественных чисел, либо сравнивают с допуском $|a - b| < \varepsilon$.

Использование: медленный оператор просто оборачивается в кэширующий. Первый вызов с данными аргументами идёт в настоящий оператор, повторные — мгновенно из кэша.

## Сравнительная таблица

| Паттерн | Где в воркшопе | Что даёт |
|---|---|---|
| Adapter | `ConstantExpression` над `double` | Подгоняет чужой тип под интерфейс |
| Composite | `BinaryOperatorExpression` с дочерними `IExpression` | Дерево из однотипных узлов |
| Bridge | `IExpression` + `IBinaryOperator` | Независимое развитие двух иерархий, один класс вместо четырёх |
| Decorator | `NegateExpression` | Добавление поведения с тем же интерфейсом |
| Proxy | Медленный и кэширующий операторы | Контроль доступа к объекту, мемоизация |

## Справочный лист

- `dotnet new sln | console | classlib | gitignore`; `.slnx` — манифест решения.
- `Directory.Build.props` — общие настройки сборки; `Directory.Packages.props` — единые версии пакетов.
- `.gitignore` — сразу после `git init`, до открытия IDE.
- `ImplicitUsings`, `Nullable` — включать для всех проектов.
- Try-паттерн: `bool TryX(..., out T result)`.
- Контекст = объект параметров, защищает сигнатуры от изменений.
- Числа в строку — `CultureInfo.InvariantCulture`.
- `switch` по кортежу: `(a, b) switch { (T1 x, T2 y) => ... }`.
- Метод расширения: `static` метод в `static` классе, `this` у первого параметра.
- `extension(T) { ... }` — свойства, статические члены и операторы в расширениях.
- `using static Type;` — статические члены без имени класса.
- `record` — структурное равенство, удобный ключ словаря.
- Декоратор при частичном результате оборачивает результат заново.

## Практические советы

- Неизменяемые объекты (record) можно безопасно возвращать как `this` и переиспользовать в деревьях.
- Если метод начинает обрастать параметрами, заверните их в контекст до того, как правка разойдётся по всем реализациям.
- Ищите в классе места, зависящие от варианта (символ, операция), и выносите их в отдельную абстракцию — так появляется мост.
- Кэшировать можно только чистые функции; с `double` в ключе помните о точности.
- DSL-сахар держите тонким слоем над объектной моделью: ядро должно работать и без него.
