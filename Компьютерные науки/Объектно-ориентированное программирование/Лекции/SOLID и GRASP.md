## Обзор лекции

Лекция посвящена двум наборам принципов проектирования модулей объектно-ориентированной системы — SOLID и GRASP. Оба набора не эксклюзивны для ООП и применимы к разработке в целом, вплоть до уровня системной архитектуры, но рассматриваются здесь на примерах классов и интерфейсов C#. По каждому принципу разбирается одна и та же схема: формулировка, пример нарушения, объяснение, почему нарушение возникает и чем оно вредно, способ исправления и польза от соблюдения. SOLID разобран полностью — все пять принципов (единственной ответственности, открытости-закрытости, подстановки Лисков, разделения интерфейса, инверсии зависимостей). Из GRASP выбраны пять принципов, наименее пересекающихся с уже пройденным материалом: Information Expert, Low Coupling / High Cohesion, Indirection, Protected Variations и Pure Fabrication.

## Предварительные сведения

- Базовые концепции ООП из предыдущей лекции: инкапсуляция, сокрытие, композиция, полиморфизм, наследование.
- Интерфейсы и абстрактные классы в C#, модификатор `virtual`/`override`.
- Понятие модуля — в контексте лекции это единица проектирования (тип, интерфейс), а не файл или папка сборки.

## Основное содержание

### Зачем нужны SOLID и GRASP

Оба набора принципов служат одной цели — сделать объектную модель расширяемой и поддерживаемой. Смысл в том, что абстракции, которыми мы моделируем предметную область, фиксируют правила устройства системы: чем яснее эти правила выражены в коде, тем сложнее случайно сломать реализацию или внести изменение, которое архитектурой не подразумевалось. Расширяемость означает, что добавление нового способа делать уже существующее действие (например, ещё один вариант операции) должно требовать только добавления нового кода, а не правки старого.

SOLID — более популярный и регулярно обсуждаемый на собеседованиях набор из пяти принципов. GRASP (General Responsibility Assignment Software Principles — «общие принципы распределения ответственностей в ПО») менее раскручен и содержит больше принципов, часть из которых пересекается с уже пройденным материалом или будет рассмотрена позже вместе с паттернами проектирования.

> [!NOTE] Уточнено по презентации
> Расшифровка «General Responsibility Assignment Software Principles» («общие принципы распределения ответственностей в ПО») приведена на титульном слайде презентации к этой теме. В самой аудиозаписи лекции она явно не звучала — лектор лишь упомянул, что название складывается «из какой-то заумной фразы», а не из слова, как SOLID. Текст расшифровки уточнён по слайду.

### S — принцип единственной ответственности (Single Responsibility Principle)

**Определение.** Тип должен иметь только одну причину для изменения. Причина изменения — это конкретное функциональное требование к системе: если у типа необходимость изменения возникает при появлении разных, не связанных друг с другом требований, тип нарушает SRP.

> [!NOTE] Дополнено
> Каноническая формулировка Роберта Мартина («a class should have only one reason to change») на лекции не звучала дословно, но лектор описывает ровно её. Добавлена для точности.

**Пример нарушения.** Есть два функциональных требования: система должна уметь генерировать отчёт в Excel и отчёт в PDF. Оба варианта реализованы как два метода одного класса-генератора. По сути это одно и то же действие (сформировать отчёт), выполняемое двумя кардинально разными способами — скорее всего, с использованием разных сторонних библиотек (одна работает с таблицами, другая с PDF).

**Почему возникает нарушение.** Изначально может показаться, что у операций есть общая часть — какая-то агрегация и трансформация данных (например, общий маппинг полей в текстовое представление). Вместо того чтобы выделить эту общую логику в отдельный тип, который можно переиспользовать извне, разработчик просто помещает оба варианта реализации в один тип, потому что «раз тут какая-то общая логика — пусть будет один класс».

**Проблемы при нарушении:**
- Сильная связанность между разными реализациями внутри одного типа: файл «засоряется» контекстом сразу нескольких технологий (IntelliSense подсказывает и типы библиотеки для Excel, и типы библиотеки для PDF, хотя в моменте нужен только один из наборов).
- Усложняется модульное тестирование: конструктор генератора должен принимать оба объекта-зависимости (например, `ExcelWriter` и `PdfWriter`), даже если тест проверяет только один сценарий — тест перестаёт быть по-настоящему изолированным.
- Больше пространства для ошибок: весь код физически лежит в одном файле, легче случайно задеть чужую реализацию при правке своей.

**Как определить нарушение:**
1. В одном классе находится абсолютно не связанная логика.
2. Несколько вариаций одного и того же действия находятся в одном классе/методе (пример выше).
3. Побочные маркеры: набор данных, необходимых для выполнения разных методов класса, почти не пересекается; аналогично почти не пересекается набор зависимостей, нужных для разных методов.

**Исправление:**
- *Декомпозиция* — разбить один тип с несколькими ответственностями на несколько отдельных типов.
- *Полиморфизм* — выделить абстракцию (интерфейс) над операцией и разнести конкретные реализации по отдельным типам, реализующим эту абстракцию. Для примера с отчётами это означает выделение интерфейса `IReportGenerator` с реализациями `ExcelReportGenerator` и `PdfReportGenerator`.

```csharp
public interface IReportGenerator
{
    void Generate(ReportData data);
}

public class ExcelReportGenerator : IReportGenerator
{
    public void Generate(ReportData data) { /* работа с Excel-библиотекой */ }
}

public class PdfReportGenerator : IReportGenerator
{
    public void Generate(ReportData data) { /* работа с PDF-библиотекой */ }
}
```
*(дополнено: конкретные имена типов и сигнатура метода не звучали в лекции дословно — восстановлены по описанному в примере смыслу)*

**Преимущества соблюдения:** более чёткая объектная модель (каждый тип в своём файле, по файловой структуре видно, какой функционал есть в системе); меньше вероятности внести ломающее изменение транзитивно (снижается «урон с наследства»); проще инициализация объектов для тестирования, так как каждому конкретному типу нужны только те зависимости, которые действительно нужны именно ему.

### O — принцип открытости/закрытости (Open/Closed Principle)

**Определение.** Логика должна быть открытой для расширения, но закрытой для изменения: должна быть возможность добавить новый способ делать что-то без необходимости менять существующую реализацию, которая уже обрабатывает похожие варианты.

> [!NOTE] Уточнено по презентации
> Этот участок транскрибации был помечен как ненадёжный; пример ниже восстановлен по слайдам презентации (реальные имена типов и код).

**Пример нарушения.** Есть перечисление `BinaryOperation` с вариантами операции (`Summation`, `Subtraction`) и класс `BinaryOperand`, хранящий два операнда. Метод `Evaluate` принимает значение перечисления и через `switch`-выражение возвращает результат нужной операции. Чтобы добавить новую операцию (например, умножение), нужно и добавить новое значение в enum, и дописать ещё одну ветку в `switch`, то есть изменить существующий метод — принцип нарушен.

```csharp
public enum BinaryOperation
{
    Summation,
    Subtraction,
}

public class BinaryOperand
{
    private readonly int _left;
    private readonly int _right;

    // ...

    public int Evaluate(BinaryOperation operation)
    {
        return operation switch
        {
            BinaryOperation.Summation => _left + _right,
            BinaryOperation.Subtraction => _left - _right,
        };
    }
}
```

**Почему возникает нарушение.** Причина обычно не в лени, а в том, что абстракция изначально выделена неправильно — не распознана точка расширения системы, то есть место, где логика структурированно варьируется. Часто это результат итеративной работы без учёта общей картины: каждое отдельное изменение (ещё один `case` в `switch`) выглядит небольшим и не страшным, но со временем таких веток накапливается много, и метод становится трудным для понимания.

**Проблемы при нарушении:**
- Все варианты реализации операции находятся в одном месте — велика вероятность случайно повлиять на один вариант, меняя логику для другого.
- Сложнее модульное тестирование: в одном методе сразу много вариантов поведения, которые надо проверять поодиночке.
- Если параметр нужен только части вариантов (например, размер шага интегрирования нужен только численному интегрированию), а хранится он на уровне всего оператора, — это создаёт путаницу: параметр приходится учитывать для всех операций, даже там, где он не имеет смысла.

**Как проверить хороший пример на OCP.** Удобный тест: представьте, что вы разрабатываете библиотеку, которая распространяется как готовый скомпилированный пакет. Если для расширения функциональности пользователю библиотеки пришлось бы редактировать исходный код самой библиотеки — принцип нарушен (правки потеряются при обновлении пакета). Если функциональность можно расширить, не трогая существующий код (например, реализовав интерфейс), принцип соблюдён.

**Исправление:** абстракция и полиморфизм. Вместо `switch` по типу операции выделяется интерфейс операции `IBinaryOperation`, а каждый вариант выносится в отдельный класс, реализующий этот интерфейс. Класс с операндами (`BinaryOperand`) хранит только значения и делегирует вычисление переданной реализации интерфейса.

```csharp
public interface IBinaryOperation
{
    int Evaluate(int left, int right);
}

public class Summation : IBinaryOperation
{
    public int Evaluate(int left, int right) => left + right;
}

public class Subtraction : IBinaryOperation
{
    public int Evaluate(int left, int right) => left - right;
}

public sealed class BinaryOperand
{
    private readonly int _left;
    private readonly int _right;

    // ...

    public int Evaluate(IBinaryOperation operation) => operation.Evaluate(_left, _right);
}
```
[Добавление новой операции — это просто новый класс, реализующий `IBinaryOperation`; существующий код не меняется вообще]

**Преимущества соблюдения:** изоляция реализаций (каждый вариант — отдельный класс); расширение формата вычислений без изменения существующей реализации (новый вариант — это новый класс); упрощение модульного тестирования — можно протестировать конкретный вариант изолированно, вызывая напрямую нужную реализацию интерфейса, а не выстраивая цепочку условий, которая доведёт выполнение до нужной ветки.

### L — принцип подстановки Лисков (Liskov Substitution Principle)

**Определение.** Назван в честь Барбары Лисков. Если дочерний тип переопределяет логику родителя, это переопределение не должно нарушать инвариант родителя: поведение наследника должно оставаться ожидаемым с точки зрения контракта, который определил родительский тип.

> [!NOTE] Дополнено
> Каноническая формулировка (объекты типа-родителя должны быть взаимозаменяемы с объектами типа-наследника без нарушения корректности программы) на лекции не звучала дословно, но соответствует описанному смыслу.

Лектор отдельно подчёркивает: LSP — по сути главное правило того, как вообще стоит проектировать иерархии наследования. Если нет уверенности, что наследование не нарушит этот принцип, лучше вообще не наследоваться, а достичь нужного через полиморфизм по интерфейсу.

**Пример нарушения.** Есть базовый класс `Creature` (существо) с методом, общим для всего живого (например, «может умереть»). От него наследуется `Bird` (птица) с виртуальным методом `Fly()` — предполагается, что «умение летать» общее для всех птиц, и конкретные птицы могут переопределять, как именно они летают.

Проблема в том, что не физиологически все птицы способны летать: например, `Penguin` (пингвин) наследует `Bird`, но не может корректно реализовать `Fly()`. Если где-то в системе есть логика миграции, принимающая коллекцию `Bird` (самый общий подходящий тип) и вызывающая `Fly()` для каждого элемента, пингвины «пытаются лететь» и падают — это прямо противоречит контракту, заданному родителем.

Вторая проблема — на другой оси: если в систему добавляется существо, которое умеет летать, но не является птицей (например, `Bat`, летучая мышь), для него метод миграции придётся обрабатывать отдельным условием (`if`) по конкретному типу. Каждое следующее подобное «летающее не-птичье» существо потребует ещё одного `if`, и любой код, работающий со всеми летающими существами, придётся аналогично дополнять веткой условия под этот новый тип.

**Почему возникает нарушение.** Разработчик обобщил поведение «умеет летать» до уровня «птица», хотя на самом деле не все птицы летают и не все летающие существа — птицы. Это частный случай более общей проблемы: попытка сделать иерархию классов «реалистичной» (как в биологической систематике — царства, классы и так далее) обычно приводит к слишком глубокой и ветвистой иерархии, с которой неудобно работать. Модель заведомо допускает отход от полного реализма ради жизнеспособности и расширяемости: модель Солнечной системы, например, не обязана в точности воспроизводить температуру Солнца, чтобы быть полезной.

**Проблемы при нарушении:**
- Сильная связанность между разными уровнями иерархии; наличие нескольких уровней наследования само по себе часто сигнализирует о проблеме в проектировании.
- Возникают частные случаи («special cases»), обрабатываемые через проверку конкретного типа (`is`/`as`/`if` по типу) — это прямо нарушает OCP: код, работающий с иерархией, приходится расширять при каждом новом подтипе.
- Реализация не соответствует ожидаемому поведению контракта — классический пример для собеседований: свойство, при обращении к которому неожиданно выбрасывается исключение (свойства по контракту должны просто возвращать данные, а не кидать исключения).
- Забывчивость: если про новый тип, добавленный в систему, «забыли» дописать обработку в нужном месте, поведение станет некорректным незаметно для разработчика.

**Как исправить.** Переосмыслить, что является настоящим общим типом и общим поведением, перепроектировать иерархию конкретных типов. Один из инструментов — «feature-интерфейс»: интерфейс, отражающий одну конкретную возможность типа, а не привязанный к биологической классификации.

```csharp
public interface ICreature
{
    void Die();
}

public interface IFlyingCreature : ICreature
{
    void Fly();
}

public class Bird : ICreature { /* умеет умирать, но не обязательно летать */ }
public class Penguin : Bird { /* просто птица, никакого Fly() */ }
public class Hummingbird : Bird, IFlyingCreature
{
    public void Fly() { /* колибри летает */ }
}
public class Bat : ICreature, IFlyingCreature
{
    public void Fly() { /* летучая мышь летает, но птицей не является */ }
}
```
[`IFlyingCreature` наследует `ICreature` — любое летающее существо всё ещё существо; но принадлежность к `Bird` больше не подразумевает автоматически умение летать. Метод миграции теперь принимает `IEnumerable<IFlyingCreature>`, и компилятор просто не даст передать туда `Penguin`]

**Преимущества соблюдения:** нет ложного родства в иерархии — реализация становится явной и не скрывает предположений «в голове разработчика»; ниже связанность между базовыми и конкретными типами на уровне иерархии.

### I — принцип разделения интерфейса (Interface Segregation Principle)

**Определение.** Клиент не должен зависеть от методов интерфейса, которыми он не пользуется — большие «толстые» интерфейсы стоит разбивать на узкие, специализированные.

**Связь с SRP.** При нарушении ISP обычно нарушается и SRP: раз интерфейс имеет несколько не связанных друг с другом обязанностей, то и у его реализации будет несколько причин для изменения. Признаки нарушения ISP такие же, как у SRP, только объектом проверки выступает не класс, а интерфейс.

**Пример из стандартной библиотеки C#.** Если декомпилировать `List<T>` (или любую коллекцию), видно, что она реализует множество интерфейсов, среди которых `ICollection<T>` и `IReadOnlyCollection<T>`:
- `IReadOnlyCollection<T>` предоставляет только количество элементов (`Count`) и возможность получить перечислитель (итератор) — то есть только чтение.
- `ICollection<T>` дополнительно предоставляет методы изменения (`Add`, `Remove`, `Clear`).

Благодаря такому разделению коллекцию можно вернуть наружу как `IReadOnlyCollection<T>` там, где изменение не подразумевается. Можно было бы просто «понадеяться», что вызывающий код не станет менять элементы полученного массива/списка, но полагаться на добросовестность потребителя — плохая практика: рано или поздно кто-то либо не подумает об этом, либо сознательно этим воспользуется. Явное сокращение доступного интерфейса убирает саму возможность совершить такую ошибку.

**Исправление:** декомпозиция — единственный применимый здесь механизм из тех, что использовались для SRP (полиморфизм тут не нужен отдельно, потому что интерфейсы и так являются абстракциями). Каждый большой интерфейс делится на несколько узких, специализированных.

```csharp
public interface IReadOnlyCollection<T>
{
    int Count { get; }
    IEnumerator<T> GetEnumerator();
}

public interface ICollection<T> : IReadOnlyCollection<T>
{
    void Add(T item);
    bool Remove(T item);
    void Clear();
}
```
[Показывает принцип разделения на примере, аналогичном интерфейсам `System.Collections.Generic`]

**Преимущества соблюдения:** соблюдается SRP на уровне интерфейсов; нет лишнего функционала у объектов конкретного интерфейса — меньше пространства для ошибок; выше модульность: если интерфейс один большой, у реализующего класса нет выбора — приходится реализовывать всё сразу; если интерфейсов несколько маленьких, их можно реализовать в одном классе, в нескольких или распределить как угодно.

### D — принцип инверсии зависимостей (Dependency Inversion Principle)

**Определение.** Правило корректной связи между уровнями абстракции и реализации.

**Классификации абстракций/реализаций, введённые для объяснения принципа:**
- *По уровню:* низкоуровневые абстракции/реализации — это относительно атомарные бизнес-правила системы (то, что раньше в курсе называлось «вариантом»), например банковский счёт; высокоуровневые — это сценарии (юзкейсы), объединяющие вызовы нескольких низкоуровневых сущностей, например сервис перевода между счетами.
- *По природе:* бизнесовые абстракции/реализации представляют саму предметную область и функциональные требования системы; инфраструктурные — не относятся к предметной области напрямую, но нужны, чтобы код вообще работал (классический пример — логирование: если убрать логи из системы, она продолжит делать ровно то же самое с точки зрения бизнес-функциональности, просто без возможности проследить выполнение).

> [!NOTE] Дополнено
> Классическая двухчастная формулировка DIP (модули верхнего уровня не должны зависеть от модулей нижнего уровня — оба должны зависеть от абстракций; абстракции не должны зависеть от деталей — детали должны зависеть от абстракций) на лекции явно не звучала в таком виде, но соответствует описанным примерам. Добавлена для полноты.

**Пример нарушения (базовый случай).** Сервис (бизнесовая реализация) напрямую хранит и использует объект конкретного класса-логгера (тоже реализация, но инфраструктурная). Если понадобится заменить консольный логгер на файловый, придётся менять сам сервис — например, конструктор сервиса — просто потому, что изменилась инфраструктурная деталь, не важная для того, что сервис реально делает.

```csharp
public class ConsoleLogger
{
    public void Log(string message) => Console.WriteLine(message);
}

public class OrderService
{
    private readonly ConsoleLogger logger = new ConsoleLogger(); // жёсткая связь с конкретной реализацией

    public void PlaceOrder()
    {
        logger.Log("Order placed");
    }
}
```

**Более тонкий пример нарушения — через тип результата.** Если метод возвращает `Result<T, TError>`, где `TError` — объединение всех возможных ошибок сразу от всех конкретных реализаций (например, «файл не найден» от одной реализации и «ошибка сети» от другой), сигнатура абстракции (интерфейса) начинает зависеть от деталей конкретных реализаций. Получается циклическая связь: реализация зависит от абстракции (реализует интерфейс), а абстракция зависит от реализации (тип ошибки в сигнатуре учитывает конкретные варианты сбоя). Циклическая связь между типами — это всегда плохо и обычно ведёт к проблемам.

**Неявные нарушения.** Принцип может нарушаться не только жёсткой связью на уровне компиляции, но и неявным контрактом: например, один класс полагается на то, что логика другого класса работает определённым образом, хотя формально это нигде не гарантировано (не описано интерфейсом). Такая неявная зависимость хуже явной — её проще случайно сломать, потому что о ней легко забыть, и заметить поломку получится только по факту (в лучшем случае — по упавшему тесту).

**Проблемы при нарушении:** сильная связанность абстракций разных уровней; изменение деталей одной реализации способно потребовать переписывания бизнес-логики, которая с этой деталью формально не связана; усложняется тестирование — сложнее подставить заглушку (mock/stub) вместо конкретной зависимости.

**Как определить нарушение:** явная связь между конкретными реализациями там, где она не обязана быть настолько жёсткой (важная оговорка: не любая прямая связь между конкретными типами — это нарушение, вопрос в том, насколько вероятны изменения и насколько нужна абстракция именно здесь); неявные, «в голове», предположения о поведении другого типа.

**Исправление:** выделение (или переосмысление) абстракции и вынесение общего контракта, обязывающего все реализации иметь одинаковый набор методов, чтобы их можно было взаимозаменяемо использовать.

```csharp
public interface ILogger
{
    void Log(string message);
}

public class ConsoleLogger : ILogger
{
    public void Log(string message) => Console.WriteLine(message);
}

public class OrderService
{
    private readonly ILogger logger;

    public OrderService(ILogger logger) => this.logger = logger;

    public void PlaceOrder() => logger.Log("Order placed");
}
```
[Стрелка зависимости на UML-диаграмме теперь направлена от `ConsoleLogger` к `ILogger`, а не наоборот — отсюда и название «инверсия»: `OrderService` зависит только от абстракции, конкретный логгер можно подменить, не трогая сервис]

**Преимущества соблюдения:** упрощается расширение (это по сути частный случай соблюдения OCP — для добавления новой реализации не нужно менять существующий код, только добавить новый класс).

### Общая идея GRASP

GRASP смотрит примерно на те же проблемы, что и SOLID, но под другим углом — со стороны того, *кому* и *как* правильно распределять ответственность между типами системы.

### Information Expert

**Определение.** Ответственность (логику обработки данных) стоит поручать тому типу, в котором эта информация фактически содержится — конкретнее, логика должна находиться там, где присутствует минимально необходимый набор данных для её выполнения.

**Пример нарушения.** Есть модель `Order` (заказ) с коллекцией `OrderLine` (позиции заказа), каждая из которых хранит цену и количество товара. Подсчёт итоговой суммы чека реализован в отдельном сервисе, который проходит по позициям заказа и явно умножает цену на количество для каждой строки. Формально логика «инкапсулирована» в сервисе, но по факту это анемичная модель (anemic model): `Order` и `OrderLine` — это чистые контейнеры данных без поведения, а вся логика вынесена в отдельный класс, оперирующий чужими данными через геттеры.

```csharp
// нарушение: расчёт вынесен в сервис, а не туда, где лежат данные
public class OrderLine
{
    public decimal Price { get; set; }
    public int Quantity { get; set; }
}

public class OrderService
{
    public decimal CalculateTotal(Order order)
    {
        decimal total = 0;
        foreach (var line in order.Lines)
            total += line.Price * line.Quantity;
        return total;
    }
}
```

**Почему это плохо.** Логика расчёта стоимости одной позиции полностью зажата внутри одного метода одного типа: если умножение цены на количество вдруг понадобится где-то ещё, придётся его дублировать. Кроме того, метод нельзя протестировать по частям — можно проверить только результат работы всего сервиса целиком, а не то, что стоимость конкретной позиции считается правильно.

**Как определить нарушение:** признак — «анемичные модели» (термин будет разбираться подробнее позже в курсе): типы, которые содержат данные, но не содержат поведения, работающего с этими данными. Если поведение, которое должно бы принадлежать таким типам, стягивается в один общий класс-«обработчик» всего на свете — это сигнал о нарушении. Дублирование одной и той же логики в нескольких местах — тоже сигнал: скорее всего, эту логику давно стоило инкапсулировать в подходящем типе.

**Исправление.** Перенести логику туда, где лежат нужные для неё данные — то есть непосредственно в `OrderLine`, а сумму заказа считать через агрегирование по позициям.

```csharp
public class OrderLine
{
    public decimal Price { get; set; }
    public int Quantity { get; set; }

    public decimal LineTotal => Price * Quantity; // минимум нужных данных — прямо здесь
}

public class Order
{
    public List<OrderLine> Lines { get; set; } = new();

    public decimal Total => Lines.Sum(line => line.LineTotal); // делегат/лямбда
}
```
[`LineTotal` теперь свойство самой позиции заказа — минимально необходимые для расчёта данные (`Price`, `Quantity`) и сама логика расчёта находятся в одном типе. `Order.Total` использует лямбда-выражение (`line => line.LineTotal`) как делегат, передаваемый в `Sum`]

**Преимущества соблюдения:** выше потенциал переиспользования (например, `LineTotal` можно использовать где угодно ещё, где нужна стоимость одной позиции); проще и точнее модульное тестирование — можно проверить расчёт одной позиции отдельно от расчёта суммы всего заказа, что упрощает локализацию проблемы при падении теста.

### Low Coupling / High Cohesion

**Определение.** Coupling (связанность) — мера зависимости модулей друг от друга в системе; чем она ниже, тем лучше. Cohesion (согласованность/связность) — мера логической соотнесённости того, что находится внутри одного модуля; чем она выше, тем лучше. Лучшее сочетание — низкий coupling и высокий cohesion; худшее — высокий coupling и низкий cohesion.

**Пример нарушения cohesion.** Один класс содержит метод, отправляющий телеметрию датчиков по HTTP, и метод, возвращающий объём используемой памяти в кэше — логической связи между этими двумя обязанностями нет вообще. Это, по сути, тот же вид проблемы, что и нарушение SRP, только рассмотренный через призму связности внутри модуля, а не через «причины для изменения».

**Пример нарушения coupling.** Класс `DataMonitor` напрямую хранит объекты конкретных классов-поставщиков данных (`DataProvider`) — то есть завязан на их конкретные типы через прямые ссылки. При появлении нового источника данных `DataMonitor` пришлось бы явно менять, чтобы он тоже умел с ним работать (по сути это ещё и нарушение OCP: сильная связанность между модулями ведёт к проблемам с расширением).

**Исправление.** Выделить абстракцию (`IDataProvider`) и завязать `DataMonitor` только на неё. Зависимость между типами системы становится ниже, потому что теперь она проходит через интерфейс, а не через конкретные типы.

```csharp
public interface IDataProvider
{
    IEnumerable<DataPoint> GetData();
}

public class DataMonitor
{
    private readonly IEnumerable<IDataProvider> providers;

    public DataMonitor(IEnumerable<IDataProvider> providers) => this.providers = providers;
}
```
[`DataMonitor` больше не знает о конкретных классах-поставщиках данных — только об абстракции `IDataProvider`]

### Indirection

**Определение.** Принцип о том, что взаимодействие между разными «кустами» бизнес-логики стоит выстраивать не напрямую, а через промежуточное звено.

**Два варианта:**
- *Через объект* («общий» Indirection) — между двумя частями логики появляется промежуточный объект, который берёт на себя часть работы: по сути это декомпозиция — кусок функционала выносится из типа в отдельный тип, а исходный код обращается к нему через объект.
- *Через интерфейс* (Indirection через абстракцию) — промежуточным звеном выступает интерфейс: это выделение абстракции, которое дополнительно повышает модульность реализации и упрощает расширение.

**Интуиция.** Чем на более мелкие модули разложена система, тем большим числом разных способов эти модули можно скомбинировать заново — аналогия с кирпичами: из маленьких кирпичей можно выложить намного больше разных форм, чем из одного большого блока.

### Protected Variations

**Определение.** Механически похож на OCP (выделение интерфейса), но мотивация принципиально другая. OCP — «оптимистичный» принцип: интерфейс выделяется заранее, потому что предполагается, что для данного функционала в будущем появится несколько разных полноценных реализаций (например, разные операции калькулятора), и мы хотим, чтобы добавление нового варианта было простым.

Protected Variations — «пессимистичный»: интерфейс добавляется не потому, что реализация должна поддерживать несколько вариантов, а потому что текущая реализация считается нестабильной, временной — требования вокруг неё могут ещё не раз измениться (классический пример — нестабильные архитектурные решения, когда, например, источник данных или базу приходится периодически менять). Интерфейс здесь работает как «буфер», ограничивающий область поражения: если нестабильная реализация меняется, переписывать приходится только саму реализацию, а весь код, работающий через интерфейс, остаётся нетронутым, потому что сам интерфейс стабилен.

### Pure Fabrication

**Определение.** В систему допустимо вносить типы, которые не соответствуют напрямую никакой сущности предметной области, если это делает систему лучше (более поддерживаемой, с более низким coupling и более высоким cohesion). Как и в случае с LSP, стремление к полному реализму объектной модели не является самоцелью — если ради качества архитектуры стоит от него немного отступить, это оправдано.

**Пример 1 — «жирный» сервис.** Класс, реализующий сразу несколько разных ответственностей (см. пример нарушения Information Expert выше), можно исправить не только переносом логики в модели, но и рассмотреть его как признак необходимости выделить дополнительные вспомогательные типы, которых в предметной области нет.

**Пример 2 — сервис как «клей».** Сервис (`Service`) — типичный пример Pure Fabrication: он представляет собой связующий («клеевой») слой, реализующий сценарий приложения — например, достать данные через репозиторий, прогнать их через бизнес-логику и сохранить результат обратно через репозиторий. Ни `Service`, ни `Repository` (абстракция доступа к данным) не являются понятиями предметной области — в реальной пекарне с булочками нет никакого «сервиса», но в программе он необходим, чтобы всё это работало вместе, будучи при этом изолированным в отдельном слое, а не размазанным по бизнес-логике.

| Принцип SOLID | Формулировка | Типичное нарушение | Способ исправления |
|---|---|---|---|
| S — Single Responsibility | Одна причина для изменения | Класс делает два не связанных дела (например, генерирует и Excel-, и PDF-отчёт) | Декомпозиция, вынесение вариантов за интерфейс |
| O — Open/Closed | Открыт для расширения, закрыт для изменения | `switch`/`if` по типу операции, который приходится дополнять | Абстракция + полиморфизм: новый вариант — новый класс |
| L — Liskov Substitution | Наследник не должен нарушать инвариант родителя | Метод, который не может корректно выполниться для части наследников (пингвин не летает) | Пересмотр иерархии, feature-интерфейсы |
| I — Interface Segregation | Клиент не должен зависеть от лишних методов интерфейса | «Толстый» интерфейс с несвязанными методами | Декомпозиция интерфейса на узкие |
| D — Dependency Inversion | Зависимость должна идти к абстракции, а не к реализации | Бизнес-класс напрямую хранит конкретный инфраструктурный тип | Выделение интерфейса, инверсия направления зависимости |

| Принцип GRASP | Суть | Ключевой вопрос |
|---|---|---|
| Information Expert | Логика — там, где данные | Где минимально необходимый набор данных для этого действия? |
| Low Coupling / High Cohesion | Меньше зависимостей между модулями, больше согласованности внутри | Насколько сильно этот модуль завязан на другие / насколько логично то, что в нём собрано? |
| Indirection | Взаимодействие через промежуточное звено | Нужен ли здесь объект- или интерфейс-посредник? |
| Protected Variations | Изоляция нестабильной части системы | Что здесь скорее всего изменится и как ограничить область поражения? |
| Pure Fabrication | Вспомогательные типы вне предметной области ради качества дизайна | Оправдан ли новый тип улучшением coupling/cohesion, даже если его «нет в реальности»? |

## Справочный лист

- SOLID: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion.
- SRP: одна причина для изменения; маркер — непересекающиеся наборы данных/зависимостей у разных методов класса.
- OCP: открыт для расширения, закрыт для изменения; тест — можно ли расширить библиотеку, не трогая её исходный код.
- LSP (Барбара Лисков): наследник не должен нарушать контракт, заданный родителем; наследование — в первую очередь механизм полиморфизма, а не переиспользования.
- ISP: клиенты не должны зависеть от неиспользуемых методов интерфейса; исправляется той же декомпозицией, что и SRP, но на уровне интерфейса.
- DIP: зависимость должна идти от конкретного к абстрактному, а не наоборот; циклическая связь абстракции и реализации — всегда плохо.
- GRASP = General Responsibility Assignment Software Patterns/Principles — «общие принципы распределения ответственности».
- Information Expert: логика — в типе с минимально необходимыми для неё данными.
- Coupling — связанность между модулями (ниже — лучше); Cohesion — логическая согласованность внутри модуля (выше — лучше).
- Indirection: посредник — объект (декомпозиция) или интерфейс (абстракция).
- Protected Variations: OCP «наоборот» — интерфейс не ради будущих вариантов, а ради изоляции уже нестабильной реализации.
- Pure Fabrication: тип может не соответствовать предметной области, если он улучшает архитектуру (пример — `Service`, `Repository`).

## Практические советы

1. Если для нового варианта поведения приходится дописывать очередную ветку `switch`/`if` в уже существующем методе — это почти всегда сигнал нарушения OCP; выносите вариант в отдельную реализацию интерфейса.
2. Проектируя иерархию наследования, в первую очередь проверяйте контракт: если наследник не может гарантированно выполнить унаследованный метод так, как ожидает вызывающий код (как пингвин с полётом), иерархию нужно перепроектировать, а не «затыкать» специальным условием по типу.
3. Не полагайтесь на добросовестность вызывающего кода там, где можно просто сузить интерфейс (например, вернуть `IReadOnlyCollection<T>` вместо `List<T>`, если изменение коллекции снаружи не предполагается).
4. Бизнес-логика не должна напрямую зависеть от конкретных инфраструктурных типов (логгеров, конкретных источников данных и т. д.) — заводите под них интерфейс, даже если реализация пока одна.
5. Если один и тот же расчёт над данными типа приходится дублировать в нескольких местах — это повод перенести его в сам тип, а не оставлять в вызывающем коде (Information Expert).
