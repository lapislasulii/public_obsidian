# ООП: теория к защите (презентации 1–2 + лабы)

> Формат: **дословное определение** → пояснение своими словами → пример из лаб.
> Л1 — первая лаба (склады и маршрутный лист), Л2 — вторая (распределение по таре).

---

## 1. Основные концепции ООП

### Инкапсуляция
> **Принцип объединения атрибутов и поведений (данных и методов) в рамках одного типа.**

- Забирает свободу размещения логики: логика не живёт сама по себе, она принадлежит типу.
- Заставляет моделировать логику в виде сущностей и явно продумывать связи между ними.
- «Метод в классе — ещё не ООП»: важно распределение данных (что сделать атрибутом, что параметром, что возвращаемым значением).

### Тип и объект
> **Тип** — шаблон, описывающий, какие данные и методы имеет объект.
> **Объект** — экземпляр типа, существующий во время выполнения кода и занимающий память.
> **Объект (с точки зрения теории ООП)** — совокупность атрибутов и поведений, реализация и данные которого скрыты от его конечного пользователя.

Запоминалка: объект в теории ООП = инкапсуляция («совокупность атрибутов и поведений») + сокрытие («скрыты от пользователя»).

### Ссылочные и значимые типы
- **Ссылочные** (`class`, `record`): данные объекта хранятся в куче, на стеке — только ссылка.
- **Значимые** (`struct`, `record struct`): данные хранятся там, где находится сам объект.
- Следствие: при присваивании значимого типа копируются данные, ссылочного — ссылка.
- Л1: значимые — `Distance`, `Velocity`, `Coordinates`, `VolumeWeight`, `Quantity`, все `...Id`; ссылочные — `Worker`, `Staff`, `Warehouse`, `Truck`, `SkuStorage`, `SkuBatch`, `Sku` (`record` без `struct` = класс).

### Состояние vs параметр
- Ориентируйтесь на предметную область: типы описывают субъекты и их операции.
- Что нужно для выполнения **всегда** → состояние (атрибут).
- Что **меняется в зависимости от контекста** → параметр.
- **Отделяйте состояние от результата**: значение, полученное в методе, не обязано быть атрибутом.
- Л1: `Worker` хранит вместимость и время (нужны всегда), а партия `SkuBatch` — параметр `RoundsFor(batch)`; число рейсов — результат, а не поле.

### Инварианты
> **Инвариант данных** — набор правил, определяющих корректное состояние данных.
> **Инвариант типа** — набор данных, их инварианта и поведений, позволяющих изменять эти данные согласно их инварианту.

### Сокрытие
> Отбирает свободу доступа к данным и поведениям. Ограничить доступ позволяют **модификаторы доступа**:
> - `public` — доступ отовсюду;
> - `private` — только внутри типа;
> - `protected` — как `private`, плюс дочерние типы;
> - `internal` — только в рамках текущей сборки (модуля).

`internal` для сокрытия в бизнес-логике — признак неправильно выстроенной абстракции.

### Инкапсуляция + сокрытие
- Позволяют **гарантировать соблюдение инварианта типа**.
- Дают **абстракцию** — «чёрный ящик» с точки зрения реализации.
- Хороший дизайн — локальные самодостаточные абстракции + их комбинация на уровне выше.

### Свойства vs поля
- Не взаимоисключающие конструкции.
- **Поля** — внутреннее состояние, которое хотим скрыть.
- **Свойства** — состояние, которое открываем наружу.
- **Цель сокрытия определяет выбор конструкции.**
- **Не отдавайте мутабельные коллекции наружу** (наружу — `IReadOnlyCollection`, изменение — через методы типа).
- Шкала мутабельности свойства: `{ get; }` (только в конструкторе) → `{ get; private set; }` (меняет только сам тип) → `{ get; set; }` (меняют все).
- Л1: `Truck.Coordinates { get; private set; }` — меняются только через `MoveTo`; `Warehouse.Coordinates { get; }` — склад не двигается.
- Л2: `Tote` хранит содержимое приватно, наружу — `IReadOnlyCollection<Item>`, добавление только через `Store` с проверкой вместимости.

## 2. Композиция

> **Композиция** — способ создания одних типов на основе других при помощи **хранения** объектов одних типов в объектах других типов.
> **Агрегация** — вид композиции, подразумевающий, что хранимые значения **получаются извне**.
> **Ассоциация** — вид композиции, подразумевающий, что хранимые значения **создаются самим объектом**.

| | Агрегация | Ассоциация |
|---|---|---|
| Откуда объект | извне (обычно через конструктор) | создаёт сам |
| Связанность | ниже — не определяем, как создаются вложенные объекты | выше — сами создаём вложенные объекты |

- Ключевое слово — **хранение**. Объект, созданный в методе и сразу возвращённый (например, `new DistributionResult.Success()`), — **не** композиция. Тест: есть ли поле этого типа?
- В одном классе бывают оба вида: в `CategoryRouter` словарь создаётся самим объектом (ассоциация), а правила в нём пришли извне (агрегация).
- Л1: `Warehouse` и `Truck` сами создают `SkuStorage`, `Warehouse` сам создаёт `Staff` → ассоциация.
- Л2: `ToteService` получает репозиторий в конструкторе → агрегация; `LoggingRule`/`FreshOnlyRule` получают `_inner` → агрегация.

## 3. Полиморфизм

> **Полиморфизм** подразумевает, что логика, написанная один раз, может выполняться по-разному.
> **Полиморфизм подтипов** (вид в ООП) — отделение абстракции от реализации, позволяющее **прозрачно использовать различные реализации посредством единого контракта**.

- «Логика, написанная один раз» — это **вызывающий код**, а не реализации. Цикл в `RouteSheet.Execute` написан один раз, а выполняет разгрузку, отгрузку или поездку в зависимости от подставленного этапа.
- Позволяет избежать излишней условной логики, моделировать вариативность типами.
- **Показывать полиморфизм — в строке вызова, а не в конструкторе:**
  - Л1: `RouteSheet.Execute` → `_stages[stageNumber].Perform(truck)`;
  - Л2: `CategoryRouter.Distribute` → `distributionRule.Distribute(item)`; `PalletRule` → `toteRule.Distribute(item)`; декораторы → `_inner.Distribute(item)`; `LoggingRule` → `_log.Write(result)`; `TimeProvider` → `FixedTimeProvider` в тестах (полиморфизм через наследование).

### Интерфейс
> Интерфейс определяет **только сигнатуры поведений**, **не определяет реализаций**, является **контрактом** к объекту типа, который его реализует. Зачастую называется абстракцией.

### Реализация vs наследование
- **Реализация** (наследование поведений) — интерфейсы; реализовывать могут и классы, и структуры. «Тип реализует интерфейс».
- **Наследование** (наследование реализаций) — базовые классы; только классы. «Класс является наследником».

### virtual vs abstract
- `virtual` — у метода **есть реализация** в базовом классе, наследник **может** переопределить (`override`).
- `abstract` — реализации **нет**, наследник **обязан** переопределить.
- `abstract`-метод — только в `abstract class`; экземпляр абстрактного класса создать нельзя.
- `virtual` — в любом не-`sealed` классе. У структур наследования нет.
- Абстрактный класс vs интерфейс: абстрактный класс может иметь состояние и реализации, наследовать можно только один; интерфейсов можно реализовать сколько угодно.
- Пример: `TimeProvider.GetUtcNow()` — `virtual`, `FixedTimeProvider` его переопределяет.

### Наследование: когда да, когда нет
- **Использовать — для реализации полиморфизма.**
- **Не использовать — для переиспользования бизнес-логики**: сильная связанность, со временем её сложнее разорвать, код сложнее рефакторить.
- Для переиспользования — **композиция** (пример со слайда: `Dealer` не наследует `Deck`, а хранит её).
- Тест: «является» (is-a) и наследник честно заменяет родителя → наследование; «имеет/использует» (has-a) → композиция.
- Л1: `Warehouse` и `Truck` не наследуют общий `StorageBase`, а хранят `SkuStorage`.

## 4. Иммутабельность

> **Свойство данных, не подразумевающее изменения.** В ООП используется в виде **сокрытия мутабельных данных** и **иммутабельности значений, не требующих изменения**.

- Минимизация мутабельности: приватное изменяемое поле + read-only представление наружу + изменение только через методы.

## 5. Обработка ошибок

> **Протёкшая абстракция** — абстракция, для работы с которой необходимо иметь знание о деталях её реализации.

### Исключения
- Не отражены в сигнатуре.
- Поиск конкретного типа исключения → протёкшая абстракция; с интерфейсами ещё хуже.
- **Неудачное выполнение операции ≠ исключительная ситуация.**
- Ошибка валидации (некорректный ввод, ошибка разработчика) — исключительная ситуация → исключение.

### Result types
- Результат операции выражается объектом; тип учитывает и успех, и негативные исходы.
- Основаны на суммах (union-типах) из ФП; в C# — закрытая иерархия: `abstract record` + **приватный конструктор** + **`sealed`** вложенные исходы.
  - приватный конструктор — нельзя унаследоваться снаружи, только вложенные типы;
  - `sealed` — нельзя унаследоваться от конкретного исхода.
- **Плюсы:** возвращаемый тип — часть сигнатуры; не нужно лезть в детали, чтобы узнать исходы; усиление контракта интерфейса; добавление новых исходов сложнее → меньше ломающих изменений.
- Это **не** полиморфизм: клиент как раз проверяет, какой исход пришёл.

### Антипаттерны result types
1. **Избыточность кейсов** — кейс под каждое место ошибки (например, на каждый атрибут валидации). Решение: один кейс + ошибка как атрибут (строка или error-object).
2. **Агрегация кейсов** — результат метода содержит сумму результатов вызываемых методов → абстракция протекла, сильная связанность. Ещё хуже — кейсы всех реализаций интерфейса.

### В Л1
- `Warehouse.Accept` бросает исключение: вызов без проверки `CanAccept` — нарушение контракта объекта, ошибка разработчика.
- `Acceptance.Perform` возвращает `StagePerformResult.InsufficientSpace`: нехватка места — законный бизнес-исход маршрута.
- `RouteSheet.DescribeFailure` переводит исходы этапа в `RouteResult.Failed` с описанием — избегаем агрегации кейсов.
- `UnreachableException` в `DescribeFailure` корректен только потому, что иерархия закрыта.

## 6. Value objects

> **Primitive obsession** — ситуация, когда доменные примитивы выражаются примитивами языка.

- Доменные примитивы могут иметь более узкую область допустимых значений → дублирующиеся валидации.
- **Value object** инкапсулирует валидацию в отдельный тип: если объект создан, валидация пройдена.
- VO представляет величину в целом, а не величину в контексте сущности (`Force`, а не `MaxForce`).
- Ошибка валидации VO — исключение (не бизнес-сценарий).

### Операторы и преобразования
- Операторы должны быть простыми и **не должны скрывать преобразования типов**.
- Перегружать арифметику — если параметры и результат **одного типа**; сравнения — можно.
- **Для преобразований между типами — методы**: не обфусцируем сам факт расчёта.
- Л1: `Velocity.From(Distance, TimeSpan)` — метод, а не `Distance / TimeSpan`.
- Приватный конструктор + фабрики (`FromMeters`, `FromKilometersPerHour`, `FromLiters`, `FromKilograms`) — единица измерения видна в вызове, перепутать нельзя.
- ⚠️ Возможный вопрос: `VolumeWeight * Quantity` — разные типы операндов. Защита: результат того же типа, что первый операнд, это масштабирование, а не преобразование.

## 7. SOLID

Общая заготовка ответа: **определение → для чего правило → пример нарушения → причины → проблемы → как определить → как исправить → преимущества**.

### S — Single Responsibility Principle
> Проектирование типов таким образом, что они имеют **единственную причину для изменения**.

- Правило для корректной инкапсуляции логики.
- Пример нарушения: `ReportGenerator` с `GenerateExcelReport` и `GeneratePdfReport`.
- Причины: «простота» (топорность — нет абстракций, низкий порог входа); переиспользование логики через приватные методы.
- Проблемы: сильная связанность разных бизнес-требований (от засорённого IntelliSense до усложнения тестирования); изменения в общем коде ломают другие решения.
- **Как определить:** несвязанная логика в одном типе; несколько способов делать одно и то же; сильное различие в наборе данных для операций; сильное различие в наборе зависимостей; один тип берёт ответственность нескольких.
- Исправить: декомпозиция, полиморфизм, выделение абстракций.
- Преимущества: чёткая объектная модель, изоляция логики, меньше влияния на другие реализации, проще модульное тестирование.
- **Когда SRP плохо:** низкоуровневый/высокопроизводительный код (каждая абстракция — косвенность, вызовы, аллокации, мешает оптимизации); чрезмерная декомпозиция (связная логика размазана, падает cohesion); маленькие скрипты/прототипы.
- Л1: `Warehouse` делегирует хранение `SkuStorage`, расчёт времени — `Staff`, сам только оркеструет; `SkuStorage` переиспользуется в `Truck`.

### O — Open/Closed Principle
> Проектирование типов таким образом, что их логику можно расширять, **не изменяя их исходный код**. Тип должен быть открыт для расширения, но закрыт для изменений.

- Правило для корректной инкапсуляции и корректного использования полиморфизма.
- Пример нарушения: `BinaryOperand` со `switch` по `enum BinaryOperation`.
- Причины: некорректное выделение абстракций; итеративная разработка без общей картины.
- Проблемы: связанность, влияние на другие реализации, нельзя протестировать реализацию изолированно.
- **Как определить:** «SRP — про типы, OCP — про реализации»; «нарушение SRP на уровне метода» = нарушение OCP. Тест библиотеки: могут ли потребители расширить её без изменения исходников?
- Исправить: определить область вариативности → выделить для неё интерфейс; полиморфизм; декомпозиция.
- Преимущества: изоляция реализаций, расширение без влияния на другие, проще тестирование.
- **Расширение ≠ добавление методов.** Расширение — новые реализации абстракции в точке расширения; код существующего типа не меняется.
- Из презентации 1: **расширение** — новый способ делать уже существующее действие; **изменение** — добавление в принципе нового функционала.
- Л1: новый этап = новый класс, реализующий `IStage`; `RouteSheet` не меняется.
- Л1 (подвох): новый **исход** этапа меняет контракт `IStage` (набор исходов — часть возвращаемого типа) → меняются `StagePerformResult` и `RouteSheet.DescribeFailure`. Это не нарушение OCP, а изменение контракта, которое закрытая иерархия делает явным.

### L — Liskov Substitution Principle
> Проектирование иерархий типов таким образом, что логика дочерних типов **не нарушает инвариант и интерфейс** родительских типов.

- Правило для корректного использования наследования и проектирования иерархий.
- Пример нарушения: `Penguin : Bird`, `FlyTo` → `Die()`.
- Причины: плохое понимание правил наследования; попытка отразить «реальные» иерархии. Реализм ≠ хороший код.
- Проблемы: сильная связанность уровней иерархии; special-case в бизнес-логике; нарушение OCP.
- **Как определить:** поведение не соответствует ожиданиям, неочевидная логика; исключения там, где их быть не должно; костыли над полиморфизмом (`obj is SomeType`); неявные связи в иерархии; «общие» поведения, присущие не всем наследникам.
- Исправить: перемоделировать иерархию; пересмотреть общие/частные типы; **feature-интерфейсы** (`IFlyingCreature`) как общие типы.
- **Преимущества:** явность реализации; более низкая связанность между базовыми и конкретными типами (клиент работает с абстракцией и не знает о конкретных наследниках).

### I — Interface Segregation Principle
> Проектирование **маленьких абстракций**, которые ответственны за свой конкретный функционал, а не одной всеобъемлющей, содержащей много различного.

- Правило для корректного проектирования интерфейсов. **ISP — это SRP для интерфейсов.**
- Пример нарушения: `ICanAllDevice` (`Print`, `PlayMusic`, `BakeBread`).
- Проблемы: абстракции обрастают поведениями, не нужными всем пользователям → больше места для ошибок; нарушение SRP у реализаций.
- Как определить: признаки как у SRP. Смотреть **со стороны клиентов**: всем ли нужен каждый метод?
- Исправить: декомпозиция.
- Преимущества: SRP у реализаций; нет лишнего функционала; меньше протечек деталей; модульность — после декомпозиции интерфейсы может реализовывать один тип, несколько, или части разные типы.
- Л1: `IStage` — один метод. Если бы понадобился `EstimateTime()` для отчёта — отдельный интерфейс (клиенту маршрута не нужна оценка, отчёту нельзя давать `Perform`).
- Правило: в интерфейсе ровно то, что вызывают его клиенты (Л2: `IToteService` — только `AddItemToTote`, `IsCompatible` остаётся приватным).

### D — Dependency Inversion Principle
> Проектирование типов таким образом, что **одни реализации не зависят от других напрямую**.

- Правило для корректного проектирования связей между типами.
- **Виды абстракций:**
  - низкоуровневая — бизнес-правила, которые могут быть переиспользованы; верхнеуровневая — конкретный сценарий, оркестрация низкоуровневых;
  - бизнесовая — отражает бизнес-логику, описывает предметную область; инфраструктурная — не часть предметной области, но необходима для работы приложения.
- Пример нарушения со слайда: `IReportStorage` с результатом `DirectoryNotFound` / `ServerNotFound` / `NetworkError` — абстракция знает детали своих реализаций.
- **Как определить:** явные связи между реализациями разного уровня/назначения (связи, **которых не должно быть**; принцип не означает, что везде нужны интерфейсы); неявные связи — код написан с расчётом на определённую реализацию; связь абстракции с её реализацией.
- Критерий «связи не должно быть»: бизнес → конкретная инфраструктура; оркестрация → исполнитель с вариативностью; A вынужден знать, *как* работает B, а не *что* он делает. Стабильные VO и доменные сущности того же уровня — норм.
- Проблемы: сильная связанность разноуровневых абстракций; детали одной влияют на другую; усложнение тестирования, **нельзя использовать mock-объекты**.
- Исправить: выделение/перепроектирование абстракций, декомпозиция.
- Преимущества: гибкость при расширении, соблюдение OCP.
- «Инверсия»: верхний уровень сам определяет нужный ему контракт, нижний его реализует.
- Л2: `ToteService` (бизнес, оркестрация) → `IToteRepository` (инфраструктура); `FreshOnlyRule` → `TimeProvider`; `LoggingRule` → `ILog`. Сервис вызывает `Update` после изменения тары — не полагается на ссылочную семантику in-memory реализации.

## 8. GRASP

> **GRASP — General Responsibility Assignment Software Principles** — общие принципы **распределения ответственностей** в ПО. (Assignment = назначить, кому поручить логику.)

Часть принципов устарела или очевидна; релевантные рассматривают те же проблемы, что SOLID, с другой стороны.

### Information Expert
> **Информация должна обрабатываться там, где она содержится.**
> Как исправить нарушение: логика должна находиться там, где находится **минимально полный набор данных**, необходимый для её реализации.

- Признаки нарушения: **анемичные модели** (данные есть, а естественная логика над ними — снаружи); перегрузка логикой; god-object; дублирование логики.
- Анемичная ≠ просто без методов: проблема, когда снаружи есть код, который должен быть методом типа. `SkuId` не анемичный — считать нечего, а валидация есть.
- Пример со слайда: `ReceiptService` считает сумму заказа вместо `Order.TotalCost`.
- Преимущества: модульность, проще переиспользовать и тестировать, соблюдение SRP.
- Л1: `SkuBatch.TotalVolumeWeight()`, `Staff.CarryingCapacity()`, `Worker.RoundsFor()`, `Coordinates.CalculateDistance()`.

### Low coupling & high cohesion
> **Coupling** (связанность) — мера зависимости модулей друг от друга. Должна быть **низкой**.
> **Cohesion** (связность) — мера логической соотнесённости логики в рамках модуля. Должна быть **высокой**.

- Low cohesion → нарушение **SRP**; high coupling → нарушение **OCP**.

### Indirection
> **Object indirection** — любое взаимодействие с данными, поведениями, модулями, реализованное не напрямую, а через какой-либо **агрегирующий их объект**.
> **Interface indirection** — то же, но через какой-либо **интерфейс**.

- Л1 object: `Acceptance` обращается к `Warehouse`, а не к `Staff`/`SkuStorage` напрямую.
- Л1 interface: `RouteSheet` → `IStage`. Л2: `PalletRule` → `IDistributionRule`.

### Protected variations
> Коррелирует с OCP, но делает **больший акцент на определении точек нестабильности**. Подразумевает выделение **стабильного интерфейса над нестабильной реализацией**.

- Запоминалка: найди точку нестабильности → закрой её стабильным интерфейсом.
- Л1: виды этапов → `IStage`. Л2: текущее время → `TimeProvider`.

### Pure fabrication
> Наличие в системе **искусственной, выдуманной сущности**, не отражающей конкретный объект моделируемых бизнес-процессов. Обычно это инфраструктурные модули, сервисы. **Не рекомендуется вносить такие типы в доменную модель.**

- Л2: репозитории, `ToteService`.

## 9. Записи (record) и равенство — на случай вопросов по коду

| Тип | Равенство по умолчанию | `==` |
|---|---|---|
| `class` | по ссылке | по ссылке |
| `record` | по значениям всех свойств | генерируется |
| `readonly record struct` | по значениям всех полей | генерируется |

- В `record` коллекция-свойство сравнивается по ссылке → для сущностей с коллекциями (например, `GoodsGroup`) переопределяем `Equals(T?)` + `GetHashCode` по `Id`.
- Свой `Equals(T?)` в не-`sealed` record обязан быть `virtual` (иначе сломается сравнение у наследников) → проще делать `sealed record`.
- Правило курса: value object — `readonly record struct`; тип с поведением и меняющимся состоянием — `class`; тип, просто хранящий атрибуты, — `record`.
